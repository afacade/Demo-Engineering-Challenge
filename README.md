# FreshFlow Recommendations Service

A small containerized service for the FreshFlow challenge. It ingests the four
CSV files through an API endpoint and serves order recommendations for a given
store and day. Built with FastAPI and SQLite.

## Getting started

Build and run with Docker:

```bash
docker build -t freshflow .
docker run -p 8000:8000 freshflow
```

The service starts empty. Load the CSVs (run from the folder that contains
`data/`):

```bash
curl -X POST http://localhost:8000/load \
  -F "items=@data/items.csv" \
  -F "orderable_items=@data/orderable_items.csv" \
  -F "inventory=@data/inventory.csv" \
  -F "order_recommendations=@data/order_recommendations.csv"
```

Then ask for recommendations:

```bash
curl "http://localhost:8000/stores/store_a/recommendations?day=2024-01-01"
```

```json
{
  "store_id": "store_a",
  "day": "2024-01-01",
  "recommendations": [
    {
      "item_number": 1001,
      "name": "Organic Bananas",
      "category": "Fruits",
      "delivery_day": "2024-01-02",
      "recommended_quantity": 18
    }
  ]
}
```

There is also an interactive UI at http://localhost:8000/docs (generated by
FastAPI) where you can upload the files and try the endpoints from the
browser.

If you want the loaded data to survive container restarts, put the database
on a volume:

```bash
docker run -p 8000:8000 -v freshflow-data:/data -e DB_PATH=/data/freshflow.db freshflow
```

## API behavior

| Situation | Response |
|---|---|
| Recommendations exist for store + day | `200` with the list |
| Valid request, but nothing for that store/day | `200` with an empty list |
| Querying before any data was loaded | `404` with a hint to call `/load` |
| `day` not in `YYYY-MM-DD` format | `400` |
| A CSV with wrong/missing columns | `400`, nothing gets ingested |

`day` matches the **ordering day** of a recommendation, since the question the
service answers is "what should this store order today". Calling `/load` again
replaces everything in one transaction, so it is safe to retry.

## Project layout

```
app/main.py   endpoints, CSV parsing and cleaning
app/db.py     schema and connection handling
tests/        API tests, including one per data-quality issue below
```

## Decisions

- **FastAPI** because the type-hinted signatures give request validation and
  the `/docs` UI for free, which makes a small API like this easy to try out.
- **SQLite** because it is a single service with small data (~25k rows per
  file): real SQL and optional persistence without running a second container.
  With multiple service instances or heavy concurrent writes I would move to
  Postgres; the queries would carry over mostly unchanged.
- **Clean identifiers at ingest, interpret values at read.** Misspelled
  identifiers (store ids, item numbers) are fixed before storing, because
  every query would otherwise have to re-solve that problem. Questionable
  values (negative quantities) are interpreted when serving, so the raw data
  stays in storage and the interpretation is easy to change.
- Recommendations are joined with the item catalog at read time so responses
  carry names and categories, not just item numbers.
- Inventory and orderable items are ingested too. Nothing reads them yet, but
  the loading path treats all four files the same and future endpoints will
  need them.

## Data quality

The provided CSVs turned out to be messy in a few ways (found by profiling
them before writing the service). What the service does about each:

- `store_id` appears as `store_a`, ` store_a`, `store_a ` and `STORE_A`
  across all per-store files. Stripped and lowercased on ingest, and the
  store id in the URL gets the same treatment before the lookup.
- ~1,900 item numbers in `order_recommendations.csv` are written as floats
  (`1001.0`), which would break the join against the catalog. Cast to
  integers on ingest.
- 240 rows in `orderable_items.csv` have a trailing comma. The extra empty
  field is ignored instead of rejecting the row or the whole file.
- ~300 rows are exact duplicates (same store, item, day and quantity, so
  dropping them loses nothing). Dropped on ingest.
- ~500 recommended quantities are negative. Served as `0`, because you
  cannot order negative pieces. In a real project I would raise this with
  whoever produces the recommendations rather than decide silently.
- ~900 recommendations reference item numbers that do not exist in
  `items.csv`. Served with `null` name and category rather than dropped,
  since the quantity is still actionable.
